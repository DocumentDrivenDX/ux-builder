## Summary

Annotations explain what each element is, what it does and why, so that
developers, designers, writers and stakeholders read the same intent from the
wireframe. Both sources favor numbered markers on the drawing with the notes in
a side column or table, instead of text written into the layout.

## Relevant Findings

- Annotate every interactive element; distinguish content notes (wording,
  tone) from functional notes (behavior).
- Document conditions and states: when an element appears, and its loading,
  error and success states.
- Explain constraints and their reasons (for example a character limit).
- Keep notes short and in plain language; avoid jargon.
- Annotate while designing, then revise for clarity.
- Detail grows with fidelity: early sketches carry ideas; higher fidelities
  carry functionality and, at the top, full interaction and content.

## Use in HELIX

Grounds `wireframe`: numbered callouts in a table, every interactive element
annotated, states covered, and annotation depth tied to the stated fidelity.
